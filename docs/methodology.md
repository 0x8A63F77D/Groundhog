# 通用方法论（蒸馏自 Lattice 项目，2026-08-17 导出）

> 来源：Lattice 项目 2026-07 至 2026-08 的全部工作流记忆 + 全局 CLAUDE.md（2026-07-13 版蒸馏）。
> 本文件只保留**项目无关**的规则；Lattice 专属细节（Avalonia/BOINC/具体 PR）已剥离，个别案例只作出处锚点。
> 适用场景：人类 Owner + AI Controller + AI 执行代理的多会话协作开发。
>
> 本文件是 Owner 交付的成品文档，在 Groundhog 仓库中作为**版本化设计工件**原样保存（见 §七.1）。

## 〇、元原则（其余一切规则的母体）

1. **唯一根原则：降低复杂度。** 两个操作动作：(a) 能不制造的复杂度不制造；(b) 无法消除的复杂度，**搬迁**到最便宜驯服它的基底（纯函数、穷举测试、形式验证可达的域）。
2. **复杂度的价格 = AI 在该域闭环验证的强度。** 同一单位复杂度在不同域价格不同：纯逻辑便宜（机器可穷举判定），UI 最贵（行为/观感无机器可判的验收信号，只能烧 Owner 的眼球时间——最稀缺资源）。设计决策跨域时，不要模式匹配最近的规则，**重算一遍"残余风险落在哪个域、我在那里的闭环多强"**。
3. **失效模式局部性剃刀：选"能力住在哪"时比较失效模式，不比较实现优雅度。** 纯函数的失效模式有界（输出错→改同一个函数→闭环可查）；自有 UI/框架机制的失效模式无界（观感对不对无法闭环，且上游框架每次更新都是暴露面）。把可承担风险的复杂度全部塞进纯函数、插进框架自己的扩展点；自有机制面积越薄越好。**注意此剃刀的输出依赖项目现状**：在一个以自绘 UI 为主的项目里，结论会翻转——不熟悉的域不要为一个小需求贸然踏入，这才是通用形。
4. **左移：问题进最合适的域，在设计时解决。** 状态机/决策逻辑从出生起就写成纯函数（显式 state-in/state-out + 转移表测试），不要等评审发现后再抽取。AI 写代码时，质量决策发生在授权/设计时——否则就不发生。
5. **有些税躲不掉——付掉。** 目标本身要求进入昂贵域时（某个效果必须做 UI 定制），付复杂度税，不要为躲税扭曲设计——"不惜代价避税"和规则崇拜是同一种失败的两个方向。**拿不准付还是躲 ⇒ 交 Owner 讨论，不要独自裁决**（这是正确执行协议，不是失败；人类自己也常拿不准）。
6. **爱好项目经济学**：理想化实现永远付得起（正当性来自工程收益，不是放纵）；技术选型可以更激进——前提是赌注可证伪（预先记录翻盘触发条件+退路）、残余风险落在闭环能兜住的层、且"确认是上游 bug→提 issue"本身算产出。此宽松**不适用于**协议/数据完整性这类产品脊柱。

## 一、会话拓扑：Controller-Chip 架构

1. **主会话 = 规划面，只做讨论、拆解、设计裁决、验收。** 实现类执行一律外派：一个 issue 一个独立执行会话（chip，各自 worktree），或后台子代理。**Controller 连自己写的小文档 PR 的评审循环也不许内联跑**——多轮循环会饱和主会话、和到达的裁决工作撞车；PR 一开（最迟循环一起）就交 chip，Controller 只裁决升级上来的语义问题。
2. **异步优先，主线程永不阻塞。** 子代理一律后台运行靠完成通知续接；主线程不坐在 sleep/等待里——用户必须随时能插话。独立任务按依赖分批并行派发。
3. **后台代理不跨会话存活**（宿主关闭即被杀，复活不可靠）：长任务（>30 分钟）的 prompt 必须要求**边执行边把阶段性结论落盘**——死了留部分成果，全损=调度事故；用户可能离线的时段不派长任务。
4. **并行隔离**：两个并行实现代理绝不共享一个 worktree（git index 竞态），各开 worktree，Controller 合并回收。并行评审共享树时，至多一个持有临时改动（证伪）权，另一个必须被告知树会脏——否则会报幽灵回归。
5. **Watcher 只报状态，不转述内容。** 监视类代理只报"发生了/出错了/超时了"+ CI 通断；发现的**内容**由主代理拉原文自己判读——转述有损，会静默丢掉高危发现（这是对信道的观察，不是对代理的不信任）。**异常（quota/报错）比预期事件更紧急**——它意味着等的事件永远不会来，必须上报，不能只报白名单形状。交给 watcher 的基线是"主张"不是事实——派发前自己核实，且让 watcher 第 0 轮复核。
6. **轮询用短促 burst**：单次 shell 调用 ≤4-5 分钟（长循环会被工具超时静默杀死）；"傻 shell 探测变化指纹，聪明模型判读语义"。chip 会话等评审时反而**该**内联轮询（它没别的事干，主线程不阻塞的理由不成立）；后台 watcher 只适合必须保持可打断的 Controller。
7. **checkpoint 的门是讨论状态，不是用户在不在。** 议题还在讨论中（用户在追问/表达不安/修正概念）→ 只给分析和提案，不开工，哪怕修法显而易见；一旦明确批准 → 放长跑，不搞中途请示表演。用户最高价值的输入是概念级转向，它只在讨论期落地——提前开工把转向变成事后返工。
8. **派发 prompt 必须自足**：任务范围、硬约束、流程规则全部写进去，不依赖执行方碰巧加载到记忆。执行方法（如"每任务开新子代理"）要用命令式写死，不写"建议"。
9. **子代理跑完后验证共享状态**：Controller 每次提交前必查当前分支——代理可能动过主 checkout。worktree 会话里**绝对路径指向主 checkout**是静默写错树的经典坑：一切读写路径建在 worktree 根下，提交前确认改动到达了 worktree。子代理的工具授权在会话启动时固定，改定义文件对已开会话无效；watcher prompt 必须带"拿不到目标工具就停下上报，禁止降级绕行"。

## 二、授权与升级（把"谁能拍板什么"结构化）

1. **升级即冻结。** 执行方一旦向 Controller 升级了任何未决问题，整个交付物转入"等答复"状态——merge/push/publish 全部冻结到答复到达。升级是"本车道不再自治"的自认；答复没到就行动，即便结果碰巧对，那是运气不是流程。派发 prompt 必须显式携带这条。Controller 侧对应义务：chip 的消息里同时出现"我将继续并合并"和一个未决问题时，**沉默会被读作同意**——想冻结就立刻回。
2. **跨会话消息 ≠ 人类授权。** 另一个 AI 会话（含 Controller）的裁决永远不构成真实用户意图；范围超出派发时人类明确授权的动作，需要 Owner 本人签字。安全分类器拦下时的正确形状：**停下、不绕过、不自行回滚、报告人类**。
3. **授权措辞会成为天花板。** 派发 prompt 里自拟的收窄措辞（如"仅文本改动可自主合并"）会被当作授权上限执行——所以合并授权要**锚定 Owner 的持久政策原文**，不要自己发明更窄的临时说法。工作流里会出现的对象（如"你将创建一个编号未知的新 PR 并在其上触发评审"）要在 prompt 里预先声明。
4. **违规后的可挽回形状**（值得固化）：立即自报、影响**实测**不猜测、不做未授权的跨分支修复、纯折腾式的回滚可以拒绝。

## 三、评审纪律

1. **自产文件不算已评审。** 自己刚写的东西交给执行方时说"落地并走正常评审"，绝不说"已定稿勿改"——单作者（包括我）必然漏东西，评审机器（外部评审、红-绿、第二模型）正是为此存在。"verbatim 照搬勿改"只保留给真正过过评审的成品（如 Owner 交付的设计包）。
2. **红-绿 + 变异证伪，双向强制。** 每个修复先复现红；评审方独立重复证伪，"红"不收口头声明。多部件修复要**逐件证伪 + 整体回退一次**——只回退其中一件得到的是中间态，不是基态。
3. **外部评审的 clean 判定要核对细节源。** 结论只在最终 commit 上有效；评审对象的摘要/状态不算数——结论后 ≥60 秒再拉一次明细线程（行内发现和评审对象共享时间戳，会晚几秒到）。反应/表态必须归因到确切作者，匿名计数不算数。quota/报错意味着这轮永远不会来——去要重置时间，别干等。
4. **评审的诊断可以对而药方错。** 遇到时用推理顶回去，不要照单执行——顺从一个错误药方和忽略一个正确诊断同样有害。
5. **重复打补丁 = 修错了地方（升级阶梯，按问题计数）：**
   - 同一组件第 2 次出现**同类**发现 → 停止改实例，点名被违反的不变量，重构让结构（作用域/类型/纯函数）强制它。趁测试网还强时做，不要推迟到"下个里程碑"。
   - 同一问题修 >3 轮 → 根因分析（形式化建模是工具之一，不是自动步骤）。
   - 根因治理后再 >3 轮 → 停下，交用户裁决。
   - 发现的**类**本身可以在第 1 次出现就正当化重构；轮数过多这个信号本身就等于"该重构了"，不要继续逐条裁决。
6. **问"问题是怎么被生产出来的"，不只问怎么修。**
   - 修法是"往下游多传一个标记让消费方补偿"→ 先问是不是数据模型选错让这个标记变得必要。让身份/不变量住进数据模型，问题的产生条件即消失（还附送免费收益）。
   - 计划里出现"把这约 40 行模板抄 N 处"→ 那是同一不变量的 N 次手抄，必然制造同类发现。把不变量抽成单份代码，计划只引用机器；手抄只用于表面（布局/文案），不变量坐进代码。
   - 计划的某节用**散文陈述多个事件处理器都要各自维持的不变量** → 那是穿着"接线"外衣的状态机，评审前就抽出来（封闭事件类型、全匹配 step、转移表测试），不要等第 11 轮。**最常见的失误不是忘了抽内核，是把状态机误分类为接线。**
7. **行为保持式重构照样会移植错语义。** "现有测试全绿"只证明被覆盖的行为；迁移时审计语义的覆盖洞并在同一变更里补测试。

## 四、证据纪律（每一条都是实际翻过车的）

1. **"改前"数据必须来自基线树。** 从基线完整回退（`git checkout origin/main -- <paths>` + 干净重建）后测量，绝不用自己工作中途某个迭代当"改前"（已提交后 `git stash` 只回退未提交部分——9/10 的"改前"图曾因此和"改后"逐字节相同）。发布前证明两者确实不同（哈希比对）；标注线要锚定**实测渲染墨迹**，不要锚定会被修复本身移动的布局框。Owner 说"我看不出差别"时，**先查证据物本身再解释感知**——两次都是证据物错了。
2. **批量/范围删除后审计幸存者。** 范围删除由端点定义，不由内容定义——漂进锚点之间的东西一起消失，构建照样绿。删除后 diff 幸存符号表 vs 上一提交，计数变化逐项对账；"差不多"就是静默删除上线的方式。优先按命名单元删除，不按行范围。
3. **外部协议的 fixture 从参考实现的发射代码誊写**（真实的 printf/序列化器），绝不从规范散文/wiki/自家文档臆写。理想化 fixture 不只是欠测——它**主动藏 bug**：解析器和 fixture 共享同一个错误假设，永远互相认可。fixture/测试注释里引用发射方文件+函数；发现旧 fixture 失真，同一变更里修掉。读发射方还能**避免**臆想的防御工事（看似威胁的输入可能根本不会出现，真 bug 在反方向）。
4. **验收文档/走查清单：逐条核对已上线代码，不核对设计意图。** README/设计文档/PR 描述描述的是意图，意图可以跑在实现前面。断言某行为存在前，grep 到它的运行时接线。清单**分步骤置备状态**时，还要审计跨步骤前置条件和共享 fixture 的角色冲突（同一实体身兼多角是同类发现的量产机）——同类第 2 次出现时，把 fixture 角色不变量在开头声明一次，不要逐步骤打补丁。
5. **廉价假设先问再建。** 写下"这个链条我现在验证不了"而人类几十秒能验证时——停下来问。区分"我现在验不了"和"没人能验"；只有后者才配"带安全回退地先建"。安全回退让错误假设**无害**，不让它**免费**——代码、边角、评审开销照付（曾有整套机制因假设为假被整体删除，还自产了两个评审发现）。问法是异步的：把问题抛出，继续建一切不依赖答案的部分，只把依赖的部分闸住。答案为否时**优先删除而非修补**——诚实的产出是一条记录在案的限制，不是一个看起来解决了问题的机制。
6. **一切二手断言都是"主张"待核实**：交给 watcher 的基线、PR 平台的元数据字段（如 base 分支 SHA 是活动指针不是分叉点）、上一轮的结论。用原始数据（merge-base、提交列表、头树 grep）判断，不用摘要字段推断。

## 五、工程方法

1. **异步/并发代码禁止盲写盲测。** 动手前先陈述并发不变量（所有交错下必须为真的东西：顺序、互斥、资源生命周期、happens-before），用结构（作用域/不可变/单一所有者/消息传递）强制之。交错正确性靠推理+必要时模型检查；绝不以"flaky 测试不再失败"作为修复依据——通过的测试对没跑到的交错什么也不证明。确无法写出确定性测试时，把推理论证诚实写进记录，不造假回归测试。
2. **疑似框架/上游 bug：确认 → 搜社区 → 再自己修。** 先排除自家代码复现（无本地覆盖、同渲染栈），再搜 upstream issues/源码找既有方案——既有方案携带边角知识，自研的即便碰巧一致也是运气不是流程。引用找到的来源，倾向社区标准形状，顺手评估是否值得给上游提 issue。
3. **函数式核心从出生开始。** 有状态决策逻辑（生命周期/重试策略/选择规则/视图状态迁移）设计时就是纯模块+转移表测试，作为计划里独立命名的任务/文件存在。理想化 ≠ 重型：纯静态类是地板，函数式语言在域契合时用，完整形式建模按升级阶梯来。
4. **确定性 UI/集成测试**：永不等待瞬态状态或可能提前变真的布尔量——settle 在期望文本或 fake 的实测调用上；墙钟等待一律禁止。测试用的调度器必须复现生产的**排序语义**，仅有互斥不等于消息队列。
5. **视觉/UI 双车道，声明式区分：** (1) 逻辑/渲染**正确性**有客观判据（渲染结果==期望）→ 机器门禁；(2) **视觉保真**（间距/字重/颜色/新图形）无机器裁判 → **禁止自主迭代**（无验收信号的自我调优=盲调，多轮反而更糟），做一版交 Owner 眼球裁决，或搁置。全新视觉表面走 Owner 的设计工具会话，工程侧只交机器验证过的功能版+截图+表面清单。headless 测试只验证你想到要断言的东西——问不出的默认值、主题叠加色、"这交互该存在吗"它都抓不到，人眼是视觉合并门。

## 六、与人协作

1. **Owner 只审概念和结果，不审框架内部。** 审不了的审批 = 橡皮图章，比没有更糟（看起来像保障）。技术评审缺口用机器补（多级评审、最强模型终审、编译期硬门禁）。
2. **交给 Owner 的每个决策项必须带三件套**：(a) **产品语言的后果**（用户会看到/经历什么，不是代码做什么）；(b) 每个被否选项的**诚实最强版**（steelman——Owner 闻不出被操纵的技术框架，所以操纵必须在结构上变难）；(c) **"什么证据能证明我错"**（可证伪把手——让 Owner 无需领域知识就能要求验证）。
3. **不要低估非技术 Owner 的贡献面。** 他们的杠杆在信号层：轮数聚合异常、品味裁决、资源分配、认识论卫生（"证据是什么级别的？出处？"——这招对任何技术主张有效且零门槛）。校准汇报方式让信号层感知保持完好：仪表盘式状态、限制同时占用注意力的事项数。
4. **面向 Owner 的报告用白话。** 无未解释的缩写、代号、轮次简写、发明的标签；技术标识符（PR 号、SHA）可以有，自造标签必须就地展开。压缩若要读者重读一遍，什么都没省。速记只允许出现在代理↔代理信道。派发 prompt 要写明"完成报告将由 Owner 阅读，白话摘要开头"。
5. **交互式提问工具通常只显示问题本身**，周边解释文字用户看不到。需要背景的问题写成回合末的正文+停下，让用户在聊天里答。

## 七、流程与追踪

1. **平台原生优先**：issues/milestones/PR body 承载追踪，不堆本地 markdown 账本——用户通过平台 UI 消费项目状态，本地账本是"对 AI 顺手、对人不友好"。执行记录进 PR body（可搜索）；规格/计划作为版本化设计工件留在 docs/。
2. **小步快跑**：一个连贯的小特性 = 一个 PR，评审+CI 全绿即按持久政策自主合并；长命分支积累风险。合并即删分支；未合并的分支没有用户点名绝不删。
3. **计划在编写时就标出 PR 切分点**；演示是合并后的展示，不是门禁。
4. **正在被本会话续写的工件，绝不交给并行会话处理**——它拿到的是过期快照。
5. **"只写文档不改代码"的任务，在文档必须断言代码从未强制的绝对属性时，就已变成代码任务。** 认证了机制并不提供的属性的文档比没文档更糟（下一个读者不再检查）。要么在唯一必经边界上强制该属性，要么显式收窄断言；措辞重写是陷阱——看似进展，实产下一轮发现。范围偏离上报 Controller 裁决，不悄悄做。
6. **YAML frontmatter 字符串里含 `: ` `#` `[` 等必须加引号**——不引会静默破坏加载，是自产文件反复翻车的经典坑（也是"自产文件不算已评审"的最佳例证）。

## 八、子代理模型分层（派发时必须显式指定，漏写就继承主会话最贵档）

| 车道 | 档位 | 适用 |
|---|---|---|
| 逐字誊写 | 最小模型 | 计划里已有完整代码，只是誊写+跑测试；守 STOP 规则最好 |
| 紧 spec 一次过的硬任务 | 中高档 | 绝不给可能迭代的活；第一轮修复失败立刻升档 |
| 难 + 迭代（调试、无紧 spec） | 高档 | 以及整分支终审（流程要求最强档） |
| 裁决/规格设计 | 主代理本人 | 语义裁决需要完整上下文，不下放 |

- 最小模型不可信之处：竞态/交错测试必假绿；红-绿的"红"必须由评审方实测复现。
- 推理力度参数按角色调（誊写 low、硬活 high）——某些区间比换模型更省。
- 拿不准路由时：派发 prompt 里加一行让子代理自选够用的最便宜档。
